## 5. 监工五条封堵逻辑（逐条）

> 定性：本节五条为**本规范新增的监工合同检查项**。截至 2026-11-06 实测，枢纽尚无实现这五条的脚本——`scripts/c2-review-hook-20261105.py` 内无 AST、空桩、红绿检查（grep 实测无命中）。五条先以“规范要求 + 手工等效命令”执行，待 §8 的 Eval 脚本落地后改由脚本执行。不得对外宣称五条已由脚本自动执行。

| # | 封堵项 | 检查方法（命令 / 判定） | 通过标准 | 失败动作 |
|---|---|---|---|---|
| ① | 源文件存在于合同路径 | `test -f <合同约定的每个源文件路径>`，逐个检查并记录输出；路径必须与合同逐字一致，不接受“差不多路径” | 合同列出的每个源文件都存在，路径逐字一致 | 任一缺失 → 打回，注明缺失的精确路径 |
| ② | AST 解析含非空函数 / 类 | `python3 -c "import ast; t=ast.parse(open('<源文件>').read());..."`：解析每个源文件，遍历 `FunctionDef / AsyncFunctionDef / ClassDef`，函数体不得只含 `pass` / `...` / 仅 docstring；类体不得为空 | 每个源文件至少含一个非空函数或非空类；AST 解析本身不得报错 | AST 解析失败，或只有空桩函数/类 → 打回，注明文件与空桩函数名 |
| ③ | verifier 控制的新目录重跑合同测试 | 监工（verifier 侧）新建空白目录，将交付物复制过去，在新目录中重跑合同测试命令；不复用 Worker 的工作目录、不复用 Worker 的缓存与已装依赖状态 | 在新目录中合同测试全部通过 | 新目录重跑失败 → 打回，注明新目录路径与失败输出 |
| ④ | 红绿检查（空桩必须失败） | 先用空桩实现（函数体只 `pass` / 返回空值）替换交付物的核心函数，重跑合同测试，必须失败（红）；再恢复真实实现重跑，必须通过（绿） | 空桩版失败、真实版通过，两次输出均留存 | 空桩版也通过（测试测不到实现）→ 打回，注明“测试无效，需补能区分空桩与实现的测试” |
| ⑤ | 只有测试输出、无源文件一律驳回 | 核对交付物清单：除测试输出/日志外，必须含合同约定的源文件；只提交测试日志、截图、口头说明的，视为无交付物 | 交付物含源文件（① 已通过）且测试输出与源文件对应同一 sha | 只有测试输出、无源文件 → 打回，不进入其余四条 |

五条为“与”关系：任一条打回即整体打回，不设“四条通过可放行”。打回后 Worker 返工须重新提交全部五条证据，不接受“只补一条”。

## 6. 监工只认三证据与感觉词禁令清单

监工验收只认三类证据：

1. **Eval 脚本输出**（Eval 脚本落地前为第 5 节规定的手工等效命令输出全文 + 退出码）；
2. **文件存在**（`test -f` / 目录清单输出）；
3. **sha256**（交付物哈希值，验收时复核一致）。

感觉词禁令清单——以下词（及同义词）**不得**出现在验收结论或打回原因中，不得作为通过或打回的理由：

> 看起来、感觉、似乎、应该、大概、差不多、基本、大致、可能、或许、我觉得、直觉上、逻辑合理、写得不错、质量还行、没问题、靠谱、稳了、显然、明显（无证据时）、想必、八成、凑合、还行、可以了、就这样吧。

违规处理：验收结论中出现禁令词，该结论无效，须重写为“证据 + 判定”格式（例：“② AST 检查：文件 `x.py` 含非空函数 `run`，通过”）。连续两次出现禁令词，监工本次验收资格暂停，改由大管家复核后重派。

## 7. Review hook 状态机（c2-verifier 第 180–230 行，实测转述）

- 触发条件：任务为 `llm_doc` 类型且合同 `review_required` 为 true 时，`c2-verifier` 自动调用 review hook。
- Hook 脚本：`scripts/c2-review-hook-20261105.py`，调用方式 `python3 <hook> --task <task_id>`，超时 300 秒。
- Kill-switch：`state/m5-20261105/REVIEW-HOOK-DISABLED` 文件存在时 hook 被旁路， verdict 记为 `BYPASSED`，写入 `state/m5-20261105/review/review-<task>-bypass.json`。
- 退出码映射（实测代码逻辑）：
- `0` = review PASS → 任务置 `DONE`（`verified_by='c2-verifier'`，`verified_at=now()`）；
- `1` = review FAIL → 任务置 `RETRY_WAIT`（`retry_count+1`，`reason=review-FAIL`），并生成返工子任务（每根任务上限 2 个，超限改为写 incident 草稿；仅针对 review 失败，不针对确定性失败）；
- 其他退出码 / 子进程异常 = ERROR：统计 `state/m5-20261105/review/` 下 `review-<task>-*.json` 的条数；**≥ 3 次 → 置 `RETRY_WAIT`（`reason=review-hook-error-x3`）**；**< 3 次 → 任务保持 `VERIFYING`，租约保留，下一分钟重试 review**（不改状态、不释放租约）。
- 租约释放：非 defer（即 PASS 或 FAIL 或 error-x3）时释放任务租约；defer 时不释放。
- 顺序保证：hook 只在 `c2-verifier` 的确定性检查已通过后运行；review 永远不能把确定性失败翻转为 DONE。
