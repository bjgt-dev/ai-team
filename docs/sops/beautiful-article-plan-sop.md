# 交付物实施 SOP：从素材到成品的 plan 驱动流程

**来源：** ConardLi/garden-skills 的 `beautiful-article` 技能（视频《Harness 实践：将任何文字编辑成精美的文章》https://www.youtube.com/watch?v=hbgVc1Oixyo 演示的正是这套技能）。
**说明：** 视频字幕未能拿到——沙箱出口 IP 被 YouTube 限流（429 + 人机验证页；字幕接口、yt-dlp、字幕站均无果）。本 SOP 以技能源文件为准（`SKILL.md` + `references/plan-template.md` + `references/harness.md` + `references/review-checklist.md` + `theme-profiles/tufte.md`），视频只是这套流程的演示，流程本身以源文件为准。
**只学方法论和流程**，不抄它的文案和主题；主题、类型名在我们自己的模板里换成自己的。

---

## 一、核心思想（三句话）

1. **先规划，后生产**：所有决策先写进一份 `plan/plan.md`，生产只执行 plan，不边做边想。
2. **三个硬检查点**：plan 定稿、首屏样张、终审交付——每个点必须停下来，等人逐项确认才能继续，禁止静默替人选。
3. **状态落盘，不靠聊天记忆**：所有已确认的决策写进文件（`source.md` / `plan.md` / `review/*.md`），长会话里忘了就回读文件，不凭记忆重新发明。

## 二、完整实施链

```
Phase 0 Intake（接单判断）
Phase 1 Source → Markdown（素材统一成 source.md）
Phase 2 Editorial Planning（只产 plan/plan.md，四段）
★ Checkpoint 1 Plan（必须停：逐项确认 5 个决策）
Phase 4 First Spread（封面 + 首屏 + 第一节 + 一个代表性视觉块）
★ Checkpoint 2 First Spread（必须停：验收 + 选开发模式 A/B）
Phase 5 Full Article Build（完整生成，单 Agent 顺序 / 多 Agent 并行）
Phase 6 Final Review（三视角终审：编辑 / 视觉 / 技术）
Phase 7 Repair（最小切片修复）
★ Checkpoint 3 Delivery（必须停：确认交付决策）
Phase 8 Delivery（交付成品 + 简短编辑说明）
```

### Phase 0 — Intake（接单判断）

- **做什么**：判断这活进不进这套流程；定初步交付物类型；记录用户期望的最终语言。
- **输入**：用户给的素材（链接 / PDF / 文档 / 文本 / 截图）或一句话需求。
- **输出**：进入 Phase 1，或停下反问（没素材不凭空构思；要的是应用不是文章则澄清，不进流程）。
- **检查点**：要的是文章还是应用？素材够不够？最终语言用户指定了吗？

### Phase 1 — Source → Markdown（素材统一）

- **做什么**：把任意输入统一成 `source/source.md`（事实底座）；不确定的写进 `source/extraction-notes.md`；用户指定目标语言且与源不一致时，先产地道翻译版 `source/source.<lang>.md`（去翻译腔，术语/数字/代码/引用保持准确），后续以翻译版为准。
- **输入**：原始素材。**输出**：`source.md` + `extraction-notes.md`（+ 需要时 `source.<lang>.md`）。
- **检查点（主 Agent 内联 5 条，不开 SubAgent，不写文件）**：抽取完整无静默丢失；数字/引用/代码准确；语言与翻译说明已记；低置信处已标注。
- **升级条件**：仅当抽取笔记标记低置信 / 复杂源时，才升级为独立 Source Reviewer SubAgent，对照原件 diff 核查，写 `review/source-review.md`。
- **回滚**：抽取错了就重抽、改 `source.md` 本身，不往后带。

### Phase 2 — Editorial Planning（只产 plan.md）

- **做什么**：只写一份 `plan/plan.md`（Brief / Outline / Theme / Assets 四段），**不直接写成品**。字段逐项见第三节。
- **输入**：`source.md`。**输出**：`plan/plan.md` 一份。
- **检查点（Plan 自查 5 条，主 Agent 内联就地核查，禁止开 SubAgent、禁止写 review 文件）**：
  1. Brief / Outline 自洽：信息保留比例与每节"保留信息"加起来对得上；Outline 没塞 Brief 没承诺的内容，也没漏 Brief 必须保留的内容。
  2. 信息取舍有据：每个"可删减"都有理由（重复 / 旁枝 / 过时）；每个"必须保留"都指向 `source.md` 的具体段落 / 表格 / 代码。
  3. 没有过度组件化：每节"需要的组件"不是把所有内容都框成卡片/引用/表格；正文仍是主体。
  4. Raw / 图片有目的：每个标注"需要 Raw"或"需要图片"的位置，都能一句话说出它服务的论点，不是装饰。
  5. 章节序号合理：连续单调（01 / 02 / 03…），子节序号前缀对齐父章节（第 08 章下只能是 8.1 / 8.2，不出现 5.1）。
- **回滚**：自查不过就地改 `plan.md` 本身，不写新文件，不进 Checkpoint 1。

### ★ Checkpoint 1 — Plan（必须停）

- **逐项确认 5 个决策，缺一不可**：① 交付物类型（含信息保留比例打包在内，不单独成题）；② 主题；③ 版式宽度；④ 配图模式（none / 用户提供 / 占位 / AI 生成，必选，不允许"默认通过"）；⑤ 封面（开 / 关）。
- **决策收集铁律**：每项独立列出、独立等答复；可以推荐（"我推荐 X，因为…"），**不能**说"已经替你定了 X，不对再说"；禁止把多项打包成一个"全部 OK 吗？"的是非题。
- **默认值要明示**：语言跟随源语言、允许编辑删减重组、TOC 默认开、先做首屏样张——开场说明里写清"如要改请告诉我"，给人反悔机会，不能藏起来。
- **回滚**：任一决策被推翻，改 `plan.md` 后重新确认；主题或版式不合适直接回到本检查点。

### Phase 4 — First Spread（先做样张，不做全文）

- **做什么**：只做"封面（若开）+ 首屏 + 第一节 + 一个代表性视觉块"。搭脚手架建工作区；第一节必须写成独立组件文件（这是后续并行的代码锚点）；封面替换占位为按主题 + 主旨定制的图文构图，外壳（比例 / 打印分页）不动。
- **输入**：确认过的 `plan.md`。**输出**：可预览的首屏样张。
- **检查点（First Spread Reviewer SubAgent，写 `review/first-spread-review.md`）**：封面 5 条自检（图文并茂、主题忠实、内容忠实、比例自适应、不与首屏重复）；首屏像文章不像落地页；第一节有阅读节奏；主题气质对；版式宽度合适；可构建、控制台无报错。
- **回滚**：按 fail 项改完再进 Checkpoint 2；主题/版式不对回 Checkpoint 1。

### ★ Checkpoint 2 — First Spread（必须停）

- **逐项确认 2 件事**：① 验收结论（通过进入完整生成 / 局部修改 / 主题或版式不合适回到 Checkpoint 1）；② 后续开发模式（A 单 Agent 顺序：最稳、风格最统一，默认；B 多 Agent 并行：最快、风格轻微差异）。
- **铁律**：两件事禁止打包成"通过 + A，OK 吗？"——人可能"通过验收但想用 B"或反之。

### Phase 5 — Full Article Build（完整生成）

- **做什么**：按 Checkpoint 2 选定的模式生成完整成品。每节必须是独立文件（`sections/NN-*.tsx`），主文件只是组装器（import 并排序各节，由主 Agent 拥有）；大型自由块同样隔离到独立文件。文件级隔离是多 Agent 并行的前提。
- **模式 A 单 Agent 顺序**：主 Agent 顺序写每节，最稳、风格最统一。
- **模式 B 多 Agent 并行**：subagent 各拥有一个节文件并行开发；主 Agent 负责合并与稳定性（维护组装顺序、跑构建/类型检查、兜底主题与风格一致、解决冲突）。
- **原则**：正文是主体；自由层（Raw）用主题 token，禁止野生样式；信息保留比例按 plan 执行；低信息密度可提高视觉块比例，但仍必须是文章形态。
- **检查点（每个 Section 一个 Section Reviewer SubAgent，以消息返回 pass/fail + 修复点，不写文件）**：完成本节 outline 任务？符合信息保留比例？必须保留的信息没丢？与前后衔接？没有过度组件化？正文充足？Raw 与配图有明确目的？本节序号自洽？
- **回滚**：fail 项主 Agent 直接修对应节文件，不重写全文。

### Phase 6 — Final Review（三视角终审）

- **做什么**：三个独立 Reviewer（可并行），结论写进 `review/final-review.md`。
- **编辑视角**：它仍然是一篇文章，不是应用；信息保留比例符合 Brief；必须保留的信息没丢；语言全文统一、地道、无残留源语言片段；没有空泛标题、堆卡片、过度总结。
- **视觉视角**：主题气质统一；自由层无野生样式；图片符合主题和上下文，不抢正文；没有明显 AI 味（装饰性视觉、紫粉渐变、圆角彩卡、假插画、emoji 装饰）；桌面和移动端都可读。
- **技术视角**：可构建、可打开、可分享；控制台无报错；代码/公式高亮与主题一致；图片有 alt、链接可用、标题层级合理；章节序号全篇自洽（与 TOC、`plan.md` Outline 三者一致，逐个抄下来比对，不要只看代码顺序）。

### Phase 7 — Repair（最小切片修复）

- **规则**：只修 fail 的项，不重跑全流程；同一层连续两次 FAIL 停下报上级；有修复才写 `review/repair-log.md`，无修复/一次过则不写。
- **禁止**：只反馈一处就重写整篇；为修视觉改动已确认的文章结构；为压缩信息删掉用户指定必须保留的内容。

### ★ Checkpoint 3 — Delivery（必须停）

- **确认交付决策一项**：通过导出 HTML / 通过同时导出 HTML + PDF / 还有局部修复（列出具体修哪里）/ 先停一停。仍要主动停下来问，不要静默走默认导出。

### Phase 8 — Delivery（交付）

- **输出**：主交付物成品文件（单文件、可离线打开、可分享）；可选 PDF（仅当 Checkpoint 3 用户选了才生成）；简短编辑说明（类型 / 信息保留比例 / 主题 / 配图策略 / 主要编辑取舍）。
- **验收**：成品可直接打开和分享；比原文更值得读；40% 信息时像被编辑过的文章而非缩水摘要；100% 信息时像被精修过的长文而非原文搬运。

## 三、plan.md 四段逐字段说明

`plan/plan.md` 是唯一规划文件，四段缺一不可。谁填：主 Agent 在 Phase 2 填；Checkpoint 1 按用户答复改。合格标准：每个字段都能在后面被执行或被核查——写不出来的字段说明还没想清楚，不许留空蒙过去。

### Brief（这篇是什么、给谁、保留多少）

| 字段 | 是干嘛的 | 填到什么程度算合格 |
|---|---|---|
| 目标读者 | 谁会读，带着什么问题 | 能说出具体人群 + 他们的问题，不是"所有人" |
| 目标语言 | 最终成品用什么语言 | 跟随源语言（默认），或指定语言；指定且与源不一致时写明源语言 → 目标语言，并注明事实底座用翻译版 |
| 文章类型 | 交付物类型，决定结构和信息保留比例 | 从类型表里选一个（见下）；不要自造类型 |
| 信息保留比例 | 成品保留源材料信息的比例 | 默认走类型标配（longform 100% · tutorial 90% · full-report / explainer / dialogue 80% · review / essay 70% · briefing 50% · visual-essay 40% · interactive-explainer ~25% 且含义是"成品里直接来自原文的句子约占 25%，其余是 AI 围绕知识点新创作的引导 + 交互"，不是删了 75%）；用户偏离标配要写实际值并加一行"非标配组合·注意事项" |
| 必须保留的信息 | 哪些内容死都不能丢 | 逐条列章节 / 表格 / 代码 / 数据 / 引用，每条指向 `source.md` 的具体位置；Section Reviewer 会逐条核对 |
| 可删减的信息 | 哪些可以不要 | 逐条列，每条带理由（重复 / 旁枝 / 过时）；没理由的不许删 |
| 语气 | 成品的语气 | 选一个：克制分析 / 出版叙事 / 决策汇报 / 教学 |
| 主要观点 | 读者要记住的判断 | 1–3 条，是判断不是话题 |
| 阅读目标 | 读完能做什么 / 知道什么 | 一句话，可检验 |
| 版式宽度 | 页面多宽 | narrow / regular / wide / full，默认 regular |
| TOC | 目录开不开 | 开 / 关，默认开 |
| 配图策略 | 图片从哪来 | none / user-assets / placeholders / ai-generated（Checkpoint 1 必确认项） |
| 封面 | 要不要书封式题图 | 开（默认）/ 关；若开，写一句构图想法 + 选定的封面模板（A 左字右图 / B 大字盖图 / C 上字下图 / D 几何拼贴 / E 极简框）+ 主视觉用什么；正式视觉在 Phase 4 落定 |

### Outline（章节锚点：每节保留什么、用什么组件）

| 字段 | 是干嘛的 | 填到什么程度算合格 |
|---|---|---|
| Hero | 首屏标题气质 / 副标题 / meta（日期·来源·作者） | 标题气质定调，不只是把原标题抄过来 |
| Lead | 导语，框定主题 | 1–2 句 |
| Summary | 是否需要结论先行 / TL;DR | 写要还是不要 |
| Sections（每节） | 编号 + 标题 + 保留信息 + 需要的组件 + 是否需要 Raw | 编号连续（01 / 02 / 03…），与最终节文件编号一致；"保留信息"写清从 source 哪几段、保留到什么程度；"需要的组件"只列真正需要的（正文仍是主体）；"是否需要 Raw"要写清服务哪个论点、表达目的 |
| 结尾方式 | 怎么收 | Conclusion / 行动项 / 留白收束，三选一 |

### Theme（选哪个主题、为什么、有没有冲突）

| 字段 | 是干嘛的 | 填到什么程度算合格 |
|---|---|---|
| 选定主题 | 用哪个主题 | 写主题 id；从已注册主题表里选，不自造 |
| 理由 | 为什么是它 | 结合源材料类型 / 语气 / 配图策略，一两句讲清 |
| 与源材料的冲突 | 主题气质和材料有没有打架 | 有则写如何处理，无则写"无"——这段的真正价值是冲突处理，不是复述主题介绍 |
| 当前信息密度下的表现建议 | 正文 / 自由层 / 图片比例如何调 | 3–5 句话足够，可引用主题 profile |

**实例（董事长截图里那篇）**：技术证据型长文 + tufte 主题，理由是 tufte 的 Data-Ink（数据墨水比）原则——页面上每一滴墨水都承载信息，去卡片、去填色、去阴影、去圆角、去装饰色，只留文字、发丝级参考线、充裕页边——与"技术证据型长文"去装化的要求一致。tufte 适合 longform / full-report / explainer / review（技术数据型）、tutorial；不适合需要远距离观看的幻灯片。

### Assets（配图计划）

| 字段 | 是干嘛的 | 填到什么程度算合格 |
|---|---|---|
| 策略 | 配图从哪来 | none / user-assets / placeholders / ai-generated，与 Brief 的配图策略一致 |
| 一句话说明 | 为什么是这个策略 | 一句话讲清；注意：自由层（Raw）始终存在，不在本段讨论——选 none 只是不用外部图片，不是不要视觉表达 |

**none 模式的完整写法（董事长截图里那篇就是这样）**：

```markdown
## Assets

- 策略：`none`
- 一句话说明：技术证据型长文 + tufte 主题的 Data-Ink 去装化原则一致。
```

none 模式下本段只有这两行，不需要逐图计划。逐图计划只在 user-assets / placeholders / ai-generated 模式下需要，每张图列：位置 / 服务的段落或论点 / 目的（建立气质 / 解释机制 / 提供证据）/ 主题 / 风格构图 / 禁止项（如 3D icon、霓虹渐变、SaaS 库存图、笑脸办公室人）/ 来源（用户文件路径 / 占位描述 / AI 生成提示词）/ 备选提示词。

## 四、plan.md 模板全文

```markdown
# Plan

## Brief

- 目标读者：<谁会读，带着什么问题>
- 目标语言：<跟随源语言（默认） / 指定语言>。若指定且与源不一致：源语言 <X> → 目标 <Y>，事实底座用翻译版 `source/source.<lang>.md`（地道、去翻译腔）
- 文章类型：<longform / full-report / tutorial / explainer / dialogue / review / essay / interactive-explainer / briefing / visual-essay>
- 信息保留比例：<X%>（默认走类型标配：longform=100% · tutorial=90% · full-report=80% · explainer=80% · dialogue=80% · review=70% · essay=70% · briefing=50% · visual-essay=40% · interactive-explainer=~25%（特例：成品里直接来自原文的句子约占 25%，其余是 AI 围绕知识点新创作的引导 + 交互）；用户偏离标配则写实际值并加一行"非标配组合·注意事项"）
- 必须保留的信息：<章节 / 表格 / 代码 / 数据 / 引用，逐条列；指向 source.md 的具体位置>
- 可删减的信息：<重复 / 旁枝 / 过时内容；每条带理由>
- 语气：<克制分析 / 出版叙事 / 决策汇报 / 教学>
- 主要观点：<这篇要让读者记住的 1-3 个判断>
- 阅读目标：<读完能做什么 / 知道什么>
- 版式宽度：<narrow / regular / wide / full>（默认 regular）
- TOC：<开 / 关>（默认开）
- 配图策略：<none / user-assets / placeholders / ai-generated>
- 封面：<开（默认） / 关>。若开，写一句构图想法 + 选定的封面模板（A 左字右图 / B 大字盖图 / C 上字下图 / D 几何拼贴 / E 极简框）+ 主视觉用什么。

## Outline

- Hero：<标题气质 / 副标题 / meta：日期·来源·作者>
- Lead：<导语，框定主题，1-2 句>
- Summary：<是否需要；放结论先行 / TL;DR>

### Sections

1. <编号 NN> <标题>
   - 保留信息：<从 source.md 哪几段，要保留到什么程度>
   - 需要的组件：<正文 + 是否 Aside/Quote/Table/CodeBlock/Formula/Image>
   - 是否需要 Raw：<是/否；若是，服务哪个论点、表达目的>
2. ...

- 结尾方式：<Conclusion / 行动项 / 留白收束>

## Theme
```

## 五、质检分工总表（哪层内联、哪层 SubAgent、写不写文件）

| 节点 | 质检方式 | 产物 | 为什么这样分 |
|---|---|---|---|
| Phase 1 Source（默认） | 主 Agent 内联 5 条 | 无文件 | 主 Agent 反正要通读 source.md |
| Phase 1 Source（仅复杂/低置信源） | Source Reviewer SubAgent，对照原件 diff | `review/source-review.md` | 静默丢失只能 diff 抓到 |
| Phase 2 Plan / Checkpoint 1 前 | 主 Agent 内联自查 5 条（禁开 SubAgent） | 无文件 | plan 是文字决策且 200–400 行，上下文是热的，SubAgent 冷启反而更慢 |
| Phase 4 First Spread / Checkpoint 2 前 | First Spread Reviewer SubAgent | `review/first-spread-review.md` | 首屏定调，多一道独立眼睛更稳 |
| Phase 5 每个 Section | Section Reviewer SubAgent | 以消息返回 pass/fail + 修复点，**不写文件** | 一篇可能 5–15 节，N 份 review 文件无人再读 |
| Phase 6 终审 / Checkpoint 3 前 | 编辑 + 视觉 + 技术 Reviewer SubAgent | `review/final-review.md` | 交付物的一部分，留档有价值 |

**铁律**：拿到任何质检结论，先按 fail 项把产出改完，再汇报"做完了 + 自检结论 + 改了什么"。直接拿原始结论汇报但不修复 = 违规。

## 六、泛化到我们的其他交付物

这套流程不只做文章。套到落地页、视频脚本、简报上时，只改三处，其余不变：

1. **Brief 的"文章类型"换成该交付物的类型**：落地页（类型 = 转化页 / 品牌页；信息保留比例换成"核心卖点保留比例"）；视频脚本（类型 = 口播 / 讲解；保留比例换成"口播稿覆盖要点比例"）；简报（类型 = briefing，保留 50% 标配）。
2. **Checkpoint 1 的 5 个决策换成该交付物的 5 个决策**：落地页——类型 / 主题 / 版式 / 配图模式 / CTA 位置；视频脚本——口播风格 / 主题 / 每章长度 / 视觉演示方式 / 是否合成音频。决策数不变（5 个），逐项确认的铁律不变。
3. **Phase 4 的"首屏样张"换成该交付物的"最小可看样张"**：落地页 = 首屏 + 第一个卖点区；视频脚本 = 第一章口播 + 一段演示画面。先让人验收样张，再做全文。

不变的：plan 先行、四段结构、三个硬检查点、每节独立文件、每节自检、终审三视角、最小切片修复、决策逐项确认禁打包。

## 七、这套流程回答的六个 Harness 问题

| Harness 部分 | 本流程解决的问题 | 设计手段 |
|---|---|---|
| 上下文管理 | 模型到底看到了什么 | 原始源统一转 `source.md`，阶段化读取参考文件 |
| 工具系统 | 能处理什么输入 / 输出 | 链接 / PDF / 文档 / 文本 / 截图 / 构建 / 浏览器检查 |
| 执行编排 | 下一步该做什么 | 分 Phase、检查点、首屏样张、完整生成、验收修复 |
| 状态与记忆 | 决策如何跨步骤保持 | `source.md`、`plan/plan.md`、`review/*.md` 落盘 |
| 评估与观测 | 怎么知道成品好不好 | Plan 内联自查；首屏/终审用 SubAgent + 写文件；每节用 SubAgent + 消息返回 |
| 约束与恢复 | 跑偏后怎么修 | 最小切片修复，禁止整篇无脑重写 |
