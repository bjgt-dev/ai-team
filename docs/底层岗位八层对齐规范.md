# 底层岗位八层对齐规范（2026-10-30）

> 原则：按岗位职责裁切，不给每个岗位塞全套八层。每个岗位只对齐与它职责相关的层，其余层由对应岗位负责，不许越界。
> 标准契约：一切新任务一律走 ceo-seat 标准 JSON 契约（任务号、目标、交付物路径、结果定义、能力需求、超时）；旧 tasks/queue 路径已冻结为遗产通道，不再接新任务。

## 总调度（OpenClaw）——对齐 L5
- L5 权限边界：只许拆解任务和派发，绝不许自己动手执行任务正文；执行一律由工人自己的认领循环完成。
- L6 调度规则：派发前校验标准 JSON 契约，不合规不派发；按工人健康档案选工人，注册表说可用不算数，工人容器没在跑就不得派发，任务回 pending 并告警。
- L8 报警接口：无可用工人时任务暂存 pending 并记告警日志，不丢单；连续失败 3 次自动禁用工人并记档。
- 2026-10-30 改动：dispatch.sh 加容器在跑守门（注册表上次验证 2026-10-17 已过期）；pi-agent 模型名单删掉已死的本地模型；头注释写明 L5 边界与遗产通道冻结。

## 主工（Worker / 执行器）——对齐 L3 + L6
- L3 认知：彻底废掉旧思维（干等、串行、一次求完美、失败记过）。可逆的直接干；失败记数据不记过错；先交 60 分可交付版本；等待超 5 分钟先诊断。
- L6 调度规则：模型一律走 model-health 动态路由，禁止写死模型名单；路由为空时取健康态模型，不猜弱模型硬上；模型失败只记模型本身的错（无响应、超时、报错），任务写不出交付物是任务或提示词的错，不许毒化模型健康态。
- 五步自救链（强制绑定）：执行失败 → 复核驳回 → 五步（搜索、问专家、执行、再验）→ 兜底三级 → 报警；五步未走完不得宣布任务失败。
- L8 报警接口：兜底耗尽、五步卡住经决策队列推给 Twt（fallback 驱动与 gate 已接线）。
- 2026-10-30 改动：agent-executor 删掉写死的兜底模型名单，改取 model-health 健康态；deliverable 缺失且模型 exit 0 时不再记模型失败（此前该 bug 把 3 个标注模型全部毒化进 24 小时冷却，导致路由一度返回空）；model-health 路由补上未标注健康模型（排在标注匹配之后，不谎称已标注）。

## 监工（Reviewer）——对齐 L7
- L7 验收：只认 Eval 验收脚本（verify-result.sh）与结果定义，按结果定义打回，不许凭感觉判断；交付物实质内容不足 100 字直接驳回（薄交付门禁）。
- L8 报警接口：驳回且无交付物证据（高危硬失败）时，立即经 notify.py 推给 Twt，带证据与 A/B 选项；普通质量驳回走复核 → 五步链，不直接报警，避免报警泛滥。
- 2026-10-30 改动：reviewer 新增 RISK_NOTIFY（驳回 + 无证据时推决策队列，任务号 reviewer-risk-开头，notify 按任务号去重）；其余验收逻辑未动（DOC_VERIFY、薄交付门禁、出口门禁均已符合 L7，予以保留）。

## 大管家（厂长）——全量对齐 L3 / L4 / L5 / L6 / L7 / L8
- L3：时间纪律与 AI 时代默认值写进席位指令（见 ceo-seat/AGENTS.md）。
- L5：只定案、调度、验收，绝不自己执行。
- L6：派发用标准 JSON 契约；模型走 model-health 动态路由；执行任务强制绑定五步链。
- L7：每轮先读 diagnose 诊断结果；巡检只报状态，不替决策。
- L8：卡壳、死信、高危立即经 notify.py 推给 Twt，带证据与 A/B；死信首次落盘即推，同一死信不重复推。
- L4：一切状态、定案、回执落盘到任务文件、决策队列、巡航文件；脑子里不存状态，Twt 随时能查岗。
- 2026-10-30 改动：ceo-seat/AGENTS.md 由单行巡航指令换成八层对齐版席位指令；ceo-opencode.sh 模型选择改取 model-health 动态路由（废除含已耗尽额度 gpt-oss-120b 的写死名单；路由为空时干净失败并记日志，由复活脚本记死信报警，不硬上弱模型）；butler_seat_revive.py 的 record_b 首次记死信即推 notify.py。

## 应急工（hub-local）——对齐 L6 + L8
- L6：平时静默，并发 1；只接抢修与兜底任务，不抢主工的活。
- L8：抢修失败或兜底耗尽立即经决策队列报警，不许静默失败。

## 巡检与可观测（L7 补齐）
- 2026-10-30 新增：每小时跑一次 model-health probe-cooldown（冷却是过期的模型重新探活），此前无此定时任务，冷却模型只能靠人工探活。
- 2026-10-30 清理：磁盘 98% → 83%（删 2613 个旧临时库文件，约 12G，正在用的已排除）；旧租约文件清理 48 个，在跑的 2 个保留；待领队列本身为空，五步积压文件不批量删（多为兜底链活任务，靠定时任务消化，批量删等于销毁自救状态）。

## 2026-10-30 15:xx 修正记录（改造后实测发现的问题，全部已修）
- 路由分两层（回归修正）：网关 /models 的 41 个模型大多不在 opencode 配置里，opencode 根本调不动；第一版改造只用网关路由，导致执行器与五步 step4 连续“无模型可用”（测试任务两次 no model responded）。修正：执行器与五步 step4 的候选一律取 opencode provider 配置里的模型名单（动态读配置，不写死），按历史成功排序实测；网关路由仍用于网关直连类任务。修正后测试任务立即用 glm-4-flash-cc 执行成功，交付物已生成。
- 模型失败归因修正：执行器与五步 step4 此前把“交付物缺失”一律记成模型失败，把 3 个标注模型全部毒化进 24 小时冷却，导致路由一度返回空。修正：只有模型本身报错（exit 非 0 / 超时）才记模型失败。
- 兜底递归根因：兜底驱动此前对 fb 任务也派生 fb2/fb3，导致 d1-debug 长链无限递归（fb3-fb2-fb3……），决策队列与报警随之泛滥。修正：兜底驱动跳过本身已含 -fb2/-fb3 的任务；已删 53 个 fb 兜底请求文件，剩余 28 个为原任务请求。五步文件本身不递归（一任务一文件），存量靠定时任务慢慢消化。
