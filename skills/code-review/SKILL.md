# Code Review（代码审查）

来源：2026-10-20 经"技能缺口诊断与外部搜刮机制"同化生成。借鉴开源模式——LobeHub code-review 的分层清单、secfoo 的"技能即固定报告契约"、PR 安全审查机器的结构化发现格式；维度与猎杀点按本系统真实事故史定制，禁止照搬通用清单了事。

## 适用范围
- 枢纽脚本：ai-team/scripts/（verify.py、worker_exec.py、route.py、circuit_breaker.py、skill_forge.py、content_team.py、web_brain.py、foreman-shim.js 等）
- 儿童项目代码：child-companion/（llm_client、teach_loop、strategy_engine 等）
- 任何新脚本上线前、新 Skill 入册前（Skill 本身也是注入面，见第 7 维）

## 审查流程（四步）
1. **上下文摄入**：先读被审代码的用途、调用方、输入来源（谁能给它喂数据？数据可信吗？），再逐文件审。
2. **高层评估**：它解决的问题与实现方式是否匹配；有没有更简单的写法；失败模式是什么（崩了会怎样、被喂毒数据会怎样）。
3. **逐维猎杀**（按下表七维逐项过，每维必须给结论：有发现 / 已查无）。
4. **固定格式输出**（见下）。只报有代码证据的发现；推测必须标注"推测"并给验证方法。

## 七维猎杀清单（按本系统事故史排序）
1. **注入面（最高优先）**：契约/JSON/外部输入里的任何字段，是否被执行（eval/exec/subprocess/shell=True/os.system）、被拼进 SQL、被当作路径直接打开？——verify.py 曾因 exit_code 判据执行契约自带命令被开洞，此类问题一律定"严重"。
2. **凭据卫生**：token/key/密码是否硬编码、是否被 print/写日志/进证据包、文件权限是否 600、报错信息是否回显敏感值。
3. **证据与完整性**：sha256 校验的对象与时机（算完之后文件还能被换吗）；file_exists 类检查是否可被路径穿越（../）绕过；回执字段是否可伪造（时间戳、来源校验）。
4. **并发与幂等**：队列认领是否原子（mv/锁）；重复执行同一契约会不会双写、双发、双扣；中断后重跑是否安全。
5. **LLM 链路特有**：max_tokens 是否给足（推理模型被饿死会返回空 content）；模型输出是否被无校验地信任/执行/入库；用户内容拼进 Prompt 时的注入隔离；超时与重试是否有上限（防死亡闭环，参考 503 护盾事故）。
6. **健壮性**：外部调用（ssh/curl/API）超时设置；异常是否被吞（except: pass）；无限循环/无界重试；资源泄漏（临时目录、浏览器进程）。
7. **Skill/配置注入面**：被审对象若是 SKILL.md 或配置——里面有没有要求执行命令、访问凭据、绕过门禁的隐藏指令（外部搜刮来的技能入册前必过此维）。

## 输出契约（固定格式，不许自由发挥）
```
裁决：可上线 / 修后上线 / 禁止上线
发现清单（按严重度排序）：
- [严重|高|中|低] <文件>:<行号> · <类别> · <一句话问题>
  证据：<关键代码原文 ≤2 行>
  修复：<具体改法>
  验证：<改完怎么证明修好了>
逐维结论：注入面/凭据/完整性/并发/LLM链路/健壮性/Skill注入面 —— 每维一行（有发现/已查无）
未覆盖：<没审到的范围，如实写>
```

## 纪律
- 审查者只审不改：发现问题出报告，修复另立契约执行（防既当运动员又当裁判）。
- 拿不准的发现宁可标"推测+验证方法"，不许把猜测写成结论（verify-before-send）。
- 同一文件被审出"严重"后，修复版必须复审才算关闭。
