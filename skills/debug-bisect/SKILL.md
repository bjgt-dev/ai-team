# debug-bisect（二分测试排障法）

## 方法（固定其他变量，只换一个组件）
1. 复现并记录基线：状态码、耗时、token 数、两端日志时间戳。
2. 二分替换：用已知可用的旧组合替换可疑组件，一次只换一个——例：旧模型 agnes-3.0-flash 回合成功（200） vs 新模型 scheduler-stable 空响应 → 病灶在"运行器 × 模型"组合，不在通道。
3. 两端日志核对：newapi 侧 GIN 日志（时间戳、源容器 IP、token 数）与调用方回执逐条对齐，验证直连是否真的生效、消费是否真的出账。
4. 定位后最小修复：能加极薄归一化层解决的，不重写核心（见 foreman-shim）。
5. 真实请求回放验收：用真实契约/真实问句回放（如 TEST-20261020-001 + 暗号复述），不许只看健康检查变绿。

## 今日案例库（2026-10-20 实证）
- **503 假象**：真根因是 newapi 自带性能护盾（performance_setting.monitor_enabled，CPU 阈值 90）被自家网关回合顶爆，自挡自重试形成死亡闭环 → 关护盾。教训：503 先查自家护盾，再怀疑上游。
- **CF schema 冲突**：Cloudflare Workers AI 要求消息 content 为纯字符串、工具呼叫消息 content 为 "" 而非 null，OpenClaw 序列化不合 → 极薄归一化代理 foreman-shim（只改消息形状、其余透传、不记内容）。其 docker unhealthy 是探针路径要认证的误报，转发链路真实可用，别修错地方。
- **/v1/v1 双拼 404**：渠道上游 URL 多拼一层 /v1（POST /v1/v1/），靠 failover 兜底才没断——日志里见 404 先数路径层数。
- **内存守卫自退**：网关 rss 超 1.5GiB 守卫线自我退出（退出码 0，不是 OOM 被杀），约 10 分钟自愈；判读日志先看退出码与守卫字样。
- **网络直连丢失**：docker network connect 的接入在容器 compose 重建后会丢——直连改造必须写进 compose 才算落地。
- **max_tokens 饿死推理模型**：llm_client 写死 100 → 推理模型 content 为空、上层报 500；生成类 ≥1500、抽取类 ≥4000。

## 避坑警告
- 护盾 + 自动重试 = 加压死循环：排障时先停重试再诊断。
- 别被探针颜色带偏：unhealthy/healthy 只说明探针路径，不说明业务链路；以真实请求回放为准。
- 主机名/端口先验明：宿主机 3012 曾是傻转发 oc-shim 而非 newapi 本体（3001→容器 3000），对着错端口排障一下午的教训。
- 同一问题连错 2 次仍无解 → 停手，按 brain-trust-router 结构化求助外脑，不许硬扛瞎猜。

## 验证标准
- 修复后真实请求 200，两端日志（时间戳/token/源 IP）逐条吻合。
- 静息指标回落（如网关 CPU 回到 ~2%），且复发条件已消除（护盾关闭已落库、直连已写 compose 等），不只是"这次通了"。
