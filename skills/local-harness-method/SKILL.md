# Harness 可迁移方法论

## 一句话定位

> 一个 Harness 不是一段提示词，而是一个小型执行系统：它回答六个问题——模型看到什么、能用什么工具、下一步做什么、决策怎么跨步骤保持、怎么知道做得好不好、跑偏了怎么修。能回答这六个问题，且答案不依赖某一家 Agent、某一个席位、某一台机器，它就能迁移。

来源：ConardLi/garden-skills（beautiful-article 的 `references/harness.md`、motion-showreel 的确定性渲染管线、web-design-engineer 的验收协议）+ 本团队 2026-11-06 实践。只取结构，不抄内容。

## Harness 要回答的六个问题

| Harness 部分 | 要解决的问题 | 我们的设计手段 |
|---|---|---|
| 上下文管理 | 模型到底看到了什么 | 输入先统一成一份事实底座文件（如 `source.md` / `plan.md`）；reference 按阶段渐进加载，不一次全读 |
| 工具系统 | 能处理什么输入 / 输出 | 能力收敛到通用工具：shell、python3、ssh、git、node、文件读写；每项能力对应一个确定性脚本 |
| 执行编排 | 下一步该做什么 | 分 Phase，每 Phase 一个可验证的产物；Phase 之间是硬检查点，不是“接着做” |
| 状态与记忆 | 决策如何跨步骤保持 | 决策落盘到状态文件（`plan.md` / `runs/<时间>/report.md` / `review/*.md`），**禁止只依赖聊天上下文记决策**；长会话不确定时回读文件，不凭记忆重发明 |
| 评估与观测 | 怎么知道做得好不好 | 每个 Phase 有机器可验的验收项，退出码判定；质检方式按节点区分（见下） |
| 约束与恢复 | 跑偏后怎么修 | 最小切片修复，禁止整盘重做；失败停在当前 Phase，修完从该 Phase 重进，不从头重跑 |

## 可迁移的五条硬规

### 规 1 · SKILL.md 是契约，不是散文

每个 Harness 一个 `SKILL.md`，frontmatter 只写两样：

```yaml
---
name: <短横线小写名>
description: "一句话：输入什么、产出什么、触发场景是什么、**不做什么**（边界比能力更重要）。"
---
```

正文必须包含：边界（先判断进不进这个 Harness）、工作流总览（Phase 图）、每个 Phase 的输入 / 动作 / 产物 / 验收、硬检查点、成功标准、相关资源表（文件 + 何时读）。

### 规 2 · 确定性脚本做事，Agent 只做判断

- 能用程序判定的事，**必须写成脚本**，不许靠 Agent 口头保证：采集、转换、比对、计数、格式校验、退出码。
- 脚本要满足：单命令可跑、输入输出写进文件、可重复跑、失败退出码非 0、**跑之前先备份要动的东西**。
- Agent 只做脚本做不了的判断：分类、取舍、向用户确认、异常定性。判断点要显式标出来，不藏在流程里。

### 规 3 · 配置与密钥外置，零写死

| 不许写死的东西 | 放在哪 |
|---|---|
| 机器名、IP、用户、绝对路径、席位名、账号名 | 一个 `config.env` / `config.yaml`，脚本开头读它；SKILL.md 里只写变量名 |
| API Key、Token、密码、cookie | Secure Vault / 枢纽 state 文件，脚本运行时读，**绝不写进 SKILL.md、脚本、日志、记忆** |
| 模型名、渠道 id、阈值、频率 | `config` 或状态文件（如 `gateway-pool.json`），改配置不改脚本 |

违反这条的 Harness 换一台机器就死，等于没迁移。

### 规 4 · 只依赖通用工具，厂商能力只作“优先 + 回退”

Harness 的关键路径只能用所有 Agent 都有（或都能装）的东西：文件读写、shell、python3、ssh、git、node、标准 CLI。

- 某一家 Agent 的私有能力（例如选择卡、专用工具）**只能写成“优先用它，没有就回退”**，并把回退路径写全。garden-skills 的范式：优先 `AskQuestion` 工具逐项确认，没有就编号列出、停下等答复——两种路径都要能走通。
- 永远不要出现“只有某某 Agent 能跑”的一步；出现即说明抽象漏了，拆出来做成脚本。

### 规 5 · 质检按节点区分，不滥用独立复核

| 节点 | 质检方式 | 产物 | 为什么 |
|---|---|---|---|
| 便宜节点（Agent 顺手能验） | 主 Agent 内联 checklist | 无文件 | 上下文是热的，开独立复核反而更慢 |
| 关键节点（定调、交付、改状态） | 独立视角复核（另一个 Agent / 另一条脚本） | 写文件留档 | 多一双独立眼睛的价值 > 开销 |
| 高频节点（一次跑 N 个同类项） | 独立复核但**以消息返回 pass/fail** | 不写文件 | N 份复核文件无人再读 |

铁律：拿到任何质检结论，**先按 fail 项把产出改完，再汇报**。只汇报结论不修复 = 违规。

## 检查点：两种停，不是“接着做”

- **用户确认型检查点**（交互式流程）：每项决策独立列出、独立等答复；可以推荐，不能静默替用户选；禁止打包成“全部 OK 吗？”一个问题。
- **验证门型检查点**（无人值守流程，如 cron 驱动的扫表、评测）：门是机器条件，**不通过就停在当前 Phase**，写报告，不进下一 Phase，不静默跳过、不拿旧结果冒充新结果。

两种检查点都必须在 SKILL.md 里标 ★，并写清“停了之后谁接、怎么恢复”。

## 多层多角度审核节点怎么设计（核心）

一个 Harness 只设一层审核（“跑通了就行”）是不合格的。garden-skills 的做法是：
**不同的审核审不同的东西，多个角度、多个层次**，每层有自己的检查清单、自己的审者、
自己的失败处理。下面是五层模型——不是每条流程都要五层全开，而是**按节点价值选层**，
选了的层必须有清单、有审者、有回滚。

### 五层分别审什么

| 层 | 审什么 | 不审什么 | 审者 | 成本 |
|---|---|---|---|---|
| **L1 结构层** | 产物形状对不对：文件在不在合同路径、字段齐不齐、格式通不通过、数量对不对 | 内容对不对、好不好看 | 脚本（程序判定） | 最低，必开 |
| **L2 事实层** | 每个数字、每个结论能不能追到源：数从哪个文件/哪条日志来、引用有没有出处、没有编造 | 文笔、风格 | 脚本比对 + 主 Agent 内联核对 | 低，必开 |
| **L3 内容层** | 说的东西全不全、对不对：有没有静默丢失、有没有漏项、判断有没有依据、边界有没有守 | 格式、风格 | 主 Agent 内联 / 独立 Agent | 中，关键节点开 |
| **L4 风格层** | 合不合家规：结论先行、短分段、不贴过程、输出脱名、没有废话 | 事实对错 | 主 Agent 内联清单 | 低，交付前开 |
| **L5 可执行层** | 跑不跑得通：退出码、测试、重跑幂等、回滚能用、换环境能跑 | 内容质量 | 脚本（测试、验收、演练） | 中，交付前开 |

再加一层**终审三视角**（只在交付节点开，学 beautiful-article 的 Final Review）：

| 视角 | 问的问题 |
|---|---|
| 编辑视角 | 它首先是它该是的东西吗（文章像文章、报告像报告）？信息取舍对吗？结构顺吗？ |
| 视觉视角 | 主题/版式/配图统一吗？移动端能读吗？有没有明显 AI 味？ |
| 技术视角 | 能构建、能打开、能分享吗？控制台干净吗？链接与引用有效吗？ |

### 每层的检查清单（照着打勾，不许凭感觉）

**L1 结构层清单**：

- [ ] 每个产物文件都在合同路径上（不在就 FAIL，不许“大概在那”）
- [ ] 必填字段齐全，缺字段即 FAIL（不许用空值蒙混）
- [ ] 数量对得上（登记行数 = 上报数，报警文件数 = 命中数，缺一即 FAIL）
- [ ] 机器可读的 verdict 文件存在（JSON，不是聊天里的口头结论）

**L2 事实层清单**：

- [ ] 报告里的每个数字都能在源文件/日志里找到（行数、条数、次数、日期，逐个能指出来）
- [ ] 每个“已完成”都有证据路径（文件 + 行号 / 日志 + 时间戳），没有证据不写完成
- [ ] 引用的结论标了来源（哪份文件、哪次实测），转述与原文分得清
- [ ] 不确定的写“未核实/待核实”，不写成肯定句；旧快照超 7 天未复核只能写“旧记录”

**L3 内容层清单**：

- [ ] 没有静默丢失：输入的每一项都有去向（做了 / 不做 + 原因 / 待核），没有“没提就是没做”
- [ ] 边界守住了（不该做的没做：没花钱、没对外发布、没动生产、没编数据）
- [ ] 每个判断都有依据（不是“我觉得”）
- [ ] 失败项有下一步（修什么、谁修、什么时候验），不是只写“失败了”

**L4 风格层清单**：

- [ ] 结论先行，报告 ≤300 字（超了就砍过程，不砍结论）
- [ ] 输出脱名：只称角色，不写真实姓名
- [ ] 不贴过程、不贴代码让用户复制、不讲“我怎么做的”
- [ ] 只报结论、阻塞、下一步三段，没有第四段

**L5 可执行层清单**：

- [ ] 脚本退出码为 0（非 0 即 FAIL，不许“看着像跑完了”）
- [ ] 测试/验收脚本全绿（有一项红即 FAIL）
- [ ] 同样输入重跑一次结果一致（不幂等即 FAIL）
- [ ] 回滚能用（备份文件存在且能恢复，不是“应该能恢复”）

**终审三视角清单**（交付节点）：编辑视角 3 问、视觉视角 3 问、技术视角 3 问，见上表；
任一视角有否决项即不交付。

### 谁审（交叉，不许自己审自己）

- **生产者 ≠ 复核者**：写东西的模型/ Agent 不能审自己的东西。复核必须用**不同供应商的模型**
  或另一个独立 Agent（这是本团队已有铁律：review 必须跨供应商）。
- **脚本审机器的事，人审判断的事**：L1、L5 必须脚本审（人才会疲劳、会放水）；L2–L4 可以人审，
  但 L2 的数字比对要先过脚本。
- **双顾问是 L3 的一种**：发散（ChatGPT：还有什么可能）与批判（Claude：哪里会翻车）是
  内容层的两个角度，不是两层——不要把“问了两个顾问”当成“过了两层审核”。
- **抽查代替全查**： steady-state 的常规轮次不值得每轮全审，按 5% 抽查 + 全量机器层；
  出问题时把抽查比例临时提到 100%，直到连续 3 轮全绿再降回去。

### 审核失败怎么回滚重做

| 失败层 | 回滚动作 | 重做范围 |
|---|---|---|
| L1 / L5（脚本判的） | 停在当前 Phase，不进下一 Phase | 只修失败项，重跑该层验收；**不从头重跑全流程** |
| L2（事实对不上） | 撤回报告里的相关结论，标“未核实” | 只补证据或改写结论，不动已通过的层 |
| L3（内容缺失/越界） | 越界动作立即停手；丢失项补进待办 | 只补缺项；越界已发生的要写进事故记录 |
| L4（风格违规） | 重写报告（只改报告，不动产物） | 只重写，不重做 |
| 终审否决 | 不交付，产物打回 | 按否决项修最小切片，修完只重审被否决的视角 |

铁律：

1. **最小切片修复**：修失败的那一项，不重写整份、不重跑全流程。修完只重审失败的层，
   通过的层不重审。
2. **两次失败升级**：同一层连续两次 FAIL，停下报父级，不许第三次硬试。
3. **修复要留档**：有修复就写 `repair-log.md`（修了什么、为什么、重审结果）；一次过不写。
4. **审核本身也要被审**：抽查发现某层长期全绿（比如 20 轮零 FAIL），要问一句是真好还是
   该层失效了（检查项太松、脚本没跑到）；连续全绿的层每季度复核一次检查项。

### 审核成本怎么控制

- **便宜层常开**：L1、L5 是脚本，一次写好每轮零成本；L2、L4 是内联清单，顺手打勾。
- **贵层只开在刀刃上**：独立 Agent 复核、双顾问、三视角终审只开在定调点（首屏、终审、
  对外交付、改生产状态）；常规轮次用抽查代替。
- **高频节点不写文件**：一次跑 N 个同类项的复核以消息返回 pass/fail，不写 N 份文件；
  只有定调与交付节点的复核写文件留档。
- **审核不是越严越好**：一层审核的成本 > 它抓到的错误的期望损失时，这层就该降级为抽查或取消。
  每季度复核一次各层的开闭。

## 一个流程够不够格包成 Harness（检查清单）

全过才值得包；有一项不过，先补那一项，不要硬包。

- [ ] 同样形状跑过 ≥3 次，且下次还会跑（一次性活不包）
- [ ] 输入、输出能枚举（说得出“进来什么、出去什么、放哪”）
- [ ] 成功能机器判定（有数字、有文件、有退出码，不靠“感觉对了”）
- [ ] 失败模式已知（至少能说出三种会怎么坏，以及坏了停在哪）
- [ ] 需要人判断的点已显式标出（不是“到时候再说”）
- [ ] 配置与密钥能外置（没有必须写死的值）
- [ ] 单次坏跑代价可控（能检测、能重跑、不污染生产状态）

## 反模式（出现一条即不合格）

- 只有提示词、没有脚本：每次靠 Agent 现场发挥。
- 路径/席位/账号写死在 SKILL.md 或脚本里。
- 静默回退：某源失败不报，拿缓存或旧结果冒充新结果。
- 记忆只存在聊天上下文：换个会话、换个席位就丢了决策。
- 验收靠 Agent 自评：没有脚本跑出的数字、文件、退出码。
- 修坏了整盘重做：没有最小切片修复和断点续跑。

## 落地顺序（每个 Harness 都走这五步）

1. **读透一个现成 Harness**（先抄结构，不抄内容）。
2. **写设计**：SKILL.md 骨架 + 脚本清单 + 验收标准，**不动生产脚本**。
3. **搭架子**：`SKILL.md` + `scripts/` + `references/` + `config.env.example`，先跑通最小一轮。
4. **实测**：真实输入跑一轮，验收脚本全绿才算落地；有一项红就修 Harness，不修生产。
5. **登记**：进技能登记表（`state/skills-registry.md`），写清状态（已装/待验/不装+原因）。
