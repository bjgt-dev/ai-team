# Karpathy 四原则：写进我们开发指导的一页

**来源：** multica-ai/andrej-karpathy-skills（230,089★，MIT），`skills/karpathy-guidelines/SKILL.md` + `CLAUDE.md` + `EXAMPLES.md`。
**落地：** 不是复制一份文件——四条原则已写进开发指导（code-dev-sop.md §七对照表），每条配一个我们自己的真实例子；plan 模板检查项待补（见末尾）。
**取舍：** 这四条偏谨慎、偏慢。小任务凭判断灵活用；复杂任务、多文件改动必须照着走。

## 1. 先想再写（Think Before Coding）

不假设、不藏困惑、把取舍摊开说。动手前：假设写出来；不确定就问；有多种理解就列出来，不悄悄替人选；有更简单的路就说出来，该顶回去就顶回去；不清楚就停下，说清哪里不清楚，再问。

**我们自己的例子——verifier 封堵 2/3/4 补齐（2026-11-06）：** 开工前先过预检门，台账 `preflight-ledger.jsonl` 2026-11-06 05:03 有一条：搜了 quant-mind 的 verify.sh（3,125★）、ECC 覆盖率门（298,221★）、agentbrain proof gates（42★，低星略过），结论是五条封堵本身没有现成实现、必须自造，但 verify.sh 的固定顺序与覆盖率门借鉴进设计。先想清楚“有没有现成的、为什么必须造”，再动手。

**反例（我们踩过的）：** 2026-11-06 19:39 装 3 小时增量扫 cron 的 subagent 没先想清楚“crontab 整表重装会清空 89 行原表”，直接覆盖安装，导致所有 cron 停死 27 分钟。先想再写，就是防这种。

## 2. 极简（Simplicity First）

用最少的代码解决问题，不写没被要求的东西：不加没要的功能、不给只用一次的代码加抽象、不加没被要求的“灵活性/可配置性”、不给不可能发生的场景写错误处理。写了 200 行、50 行能解决就重写。问自己：资深工程师会不会说这过度复杂了？会就简化。

**我们自己的例子——`preflight.sh`（2026-11-06）：** 41 行，只做两件事：`log` 记一条预检、`check` 查有没有记录。没加审批流、没加锁、没加通知、没加 Web 界面。台账就是 JSONL 追加一行，检查就是 grep 一行。够用就停。

## 3. 手术式改动（Surgical Changes）

只碰必须碰的，自己的烂摊子自己收。改现有代码时：不“顺手改进”旁边的代码、注释、格式；不重构没坏的东西；风格跟现有代码走，哪怕自己会换种写法；看到无关的死代码，只提一句，不删。自己改动产生的孤儿（没再用的 import、变量、函数）要清掉；改动前就有的死代码，没被要求就不删。检验标准：每一行改动都能直接追到用户的需求。

**我们自己的例子——技能看板 33→40 修正（2026-11-06）：** 只改数字（33→40）与漏掉的 7 个技能名，按原分组归类；分组计数由 JS 按数组长度自动算，不手改；快照日期不动；改完 grep 核查页面无“33”残留。没动结构、没动样式、没动别的卡。

**反例（我们踩过的）：** 同一条，19:39 的 cron 事故就是反面：装一行 cron 的任务改了整张 89 行的表——改动范围远超需求本身。

## 4. 目标驱动（Goal-Driven Execution）

把任务翻成可验证的目标，循环直到验证通过。“加校验”→“先给非法输入写测试，再让它通过”；“修 Bug”→“先写能复现的测试，再让它通过”；“重构 X”→“重构前后测试都通过”。多步骤任务先写简短计划，每步带验证方法。强标准能让人独立循环；弱标准（“让它能跑”）只会让人反复来问。

**我们自己的例子——M5 压缩法 7 窗口（2026-11-06）：** 每个窗口 6 项验收写在 `state/m5-20261105/recalc-20261106/window-20261105-2030.md`（非 L3 人工介入 0、经验收交付 ≥1 件/日、假 DONE 0、 pending 最老 <30 分钟、Tier-1 全窗口 ≥2、成本 0），≥6 个窗口全过才报 M5 过。M4 golden-set-100 以 85 分为线，80/100 差 5 分，禁止改题凑分——目标写死了，才没人敢拿“感觉差不多了”蒙混。
