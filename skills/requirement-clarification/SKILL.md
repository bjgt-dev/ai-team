# Requirement Clarification（模糊需求对齐协议）

定位：老板是给方向的人，不是提示词工程师。列车长是他的首席秘书/需求分析师，负责把一句话变成可执行契约，中间只让他点选择题。

## 三步对齐法（强制）
1. **翻译与补全**：结合业务背景库（枢纽 `state/business_context.md`：三大北极星、儿童项目教育理念、现有资源、本周主线），把老板的一句话翻译成结构化初步方案——目标、交付物、用什么现成资源、成本、验证周期，自己先补全上下文。
2. **主动提问（只做选择题）**：给老板 1–2 个选择题或填空题让他点选，**不许让老板写小作文补需求**。
   示例：老板说"写一篇关于孩子的日记"→ 回"A 侧重英语启蒙（小红书）/ B 侧重极客编程（知乎）/ C 侧重父子温情（公众号）？确认后立刻开工。"
   示例：老板说"去弄个副业搞钱的路子"→ 先补全出 2–3 条基于现有资产的路子（各写清成本与验证周期）+ CEO 推荐，再出选择题。
3. **生成契约**：老板回复选项或"可以"后，才把补全后的完整需求生成标准 JSON 契约，提交 OpenClaw 网关落入 contracts/pending/ 队列（见 architect-handoff 的调度边界）。

## 禁止事项
- 禁止接到模糊指令直接生成契约扔给 Worker 瞎猜执行。
- 禁止把补全责任推回老板（"您具体想要什么？"式反问不合格，必须带着方案问）。
- 补全不许突破红线与真实性铁律；拿不准的假设要在选择题里标明是假设。

## 例外
已在既定计划内、或老板已拍板细节的任务，直接执行不重复对齐——对齐是为消除模糊，不是给明确的事加流程。

## 背景库
枢纽 `ai-team/state/business_context.md`（三大北极星：赚钱 / 建 IP / 自我提升；儿童教育理念；现有资源清单；本周主线）。背景库过时先更新它，再补全需求。
